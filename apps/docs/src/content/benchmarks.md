# Benchmarks

This page is for engineers who evaluate Syncular's performance or reproduce a
measurement. It lists the recorded numbers for bootstrap, realtime propagation,
bundle size, server memory, blobs, and imports, states what each lane measures
and leaves out, and documents the diagnostic workloads that the harness in
[`bench/`](https://github.com/syncular/syncular/tree/main/bench) runs.

::meta{for="Engineers evaluating or reproducing performance" time="Reference" first="concepts-bootstrap"}

:::terms
- **Loopback lane**: The TypeScript client core and the real server library exchange SSP2 bytes in one process. Transport, segment download, and realtime are function calls.
- **Rows lane**: Bootstrap through rows segments: the server scans, encodes, and hash-verifies the rows for each bootstrap.
- **SQLite image**: A precomputed SQLite file segment the server builds once per (scopes, pin) and every later client imports ([Bootstrap & segments](/concepts-bootstrap/)).
- **Workload**: One diagnostic scenario selected with `bun run bench --workload <name>`.
:::

## Methodology and caveats

The published numbers come from the loopback lane. The client runs in the same
process as the server on bun:sqlite, so a browser client on sqlite-wasm
differs. The lane isolates engine cost; a deployment adds the network and
serialization costs it leaves out. Every row has six small columns (`id`,
`project_id`, `title`, `done`, `priority`, `updated_at_ms`).

:::note{title="How to read the numbers"}
Timings vary from run to run. Medians come from the run counts stated per
section, after one discarded warm-up. `RESULTS.md` records the host core count
and the 1-minute load average at the start of the run; this record is the
median-image-lane run of five consecutive runs on a host that other processes
kept at load 3.3 to 7.1 (start loads 6.4, 7.1, 3.5, 3.3, 3.4). Across those five
runs the rows lane ranged 364.1 to 536.6 ms, the image lane 40.4 to 47.2 ms, and
the realtime p95 0.8 to 3.4 ms; the two runs at load above 6 produced the
slowest rows-lane and highest realtime values. Sizes use KiB (1024 bytes). The
size gate counts Syncular's bytes only; every wasm-SQLite product ships the
stock SQLite distribution, so vendor bytes do not gate. The diagnostic workloads below use separate lanes and write
JSON artifacts instead of changing the curated record.

Reproduce the loopback numbers with:

```sh
git clone https://github.com/syncular/syncular
cd syncular
bun install
bun run bench
```

The harness prints the same tables on your machine. Absolute values differ from
the recorded darwin/arm64 run. Repository benchmark commands require Bun 1.4.0
or newer, because older Linux Bun builds report subprocess peak memory in
different units.

All runs, in ms:

## Windowed sync

A window replace from `{A,B}` to `{B,C}` downloads only C. The intersection B is
neither re-bootstrapped nor evicted (SPEC §4.8). The rows-lane segment counter
holds 500 rows per project:

| Step | Bootstrap rows applied |
|---|---:|
| Initial window `{A,B}` | 1,000 |
| Replace `{A,B}` with `{B,C}` | 500 |
| Naive re-download of A, B, and C | 1,500 |

The cost of a window change grows with the delta, not the window size. The
benchmark asserts that B was not re-downloaded.

A page that uses the worker setup loads 59.8 KiB of Syncular code gzipped plus

overstates what a typical page loads.

## Server memory

Peak RSS delta during the 100k-row bootstrap: **100.9 MiB**, sampled every 2 ms.
The five runs ranged from 44.8 to 177.2 MiB, so treat a single value as indicative only.
Server and client share one process in this lane, so the delta includes the
client's local SQLite writes. Read it as an upper bound on the server share.

## Blob state

The SQLite client stores blobs with immutable body rows, upload state in a small
separate row, and commit dependencies written directly with each outbox commit.
It keeps no stored refcounts, triggers, startup backfill, or cache-hit writes,
and it reads live references only during cache retention. A fresh download
checkpoints its completed body from the write-ahead log before it returns.

Two independent collections measured upload of one 500,000,000-byte blob. Each
ran ten paired attempts per core with fresh writer and reader processes,
WAL/FULL client databases, a pinned MinIO container per attempt, and complete
SHA-256 receipts:

| Collection | Core | Upload median |
|---|---|---:|
| First | TS | 1,454.29 ms |
| Confirmation | TS | 1,524.89 ms |
| First | Rust | 1,993.12 ms |
| Confirmation | Rust | 2,027.48 ms |

A third check ran the published TS and Rust clients against a verified server in
three alternating pairs per core, with no retries or exclusions and every
SHA-256 receipt verified. Medians:

| Core | Clock boundary | Median |
|---|---|---:|
| JS | Total upload | 3,006.24 ms |
| JS | Upload after staging | 1,470.24 ms |
| Rust | Total upload | 3,765.50 ms |

Source: `bench/RESULTS.md` and the `offline-sync-bench` investigation

### Blob download with 100,000 visible references

The file profile downloads one 65,536-byte object into a persistent client that
holds 100,000 visible `blob_ref` values, through MinIO. The clock covers
transport, SHA-256 validation, SQLite cache insertion, reference reconciliation,
cache-cap enforcement, and complete byte materialization. Fixture creation and
the final digest check sit outside it. Each core ran two collections of ten
paired blocks:

| Collection | Core | Median |
|---|---|---:|
| First | TS | 18.78 ms |
| First | Rust | 15.75 ms |
| Confirmation | TS | 18.97 ms |

## Sparse patch payloads

`bench/src/patch-lane.ts` queues 500 `patch` calls, each writing two of twenty
columns on a distinct seeded row, then drains them in one sync round on the
loopback lane (RFC-WRITE-SEMANTICS §11). A patch sends a presence bitmap that
names the primary key and the two written columns. The drain coalesces all 500
commits into one push request.

| Metric | Measured |
|---|---:|
| Request bytes, 500 patches | 57,866 |
| Request bytes if each patch sent the full twenty-column row | 123,756 |
| Response bytes | 170,646 |
| Drain time, median | 38.1 ms |
| Drain time, range | 36.2 to 49.9 ms |

Six trials on one host (Apple M4, Bun 1.4.0). Request and response bytes repeat
exactly across trials; drain time varies by about 14 ms within a side. The
response bytes are the same for both shapes because `COMMIT` delivery uses the
full-row codec. Reproduce with `bun run --cwd bench bench:patch 3`.

## Responsiveness of large imports

`bench/src/responsiveness.ts` imports synthetic SSP2 responses into fresh
in-memory bun:sqlite databases with managed FTS, with one warmup and three
measured trials per format and size (Apple M4, Bun 1.4.0). The import commits in
chunks. A read queued after the first committed chunk returns while the rest of
the import is pending:

| Format | Rows | Complete import | First read | Eviction |
|---|---:|---:|---:|---:|
| Rows | 2,500 | 26.15 ms | 10.74 ms | 5.10 ms |
| Rows | 5,000 | 50.67 ms | 12.09 ms | 10.06 ms |
| Rows | 10,000 | 99.24 ms | 13.98 ms | 20.02 ms |
| SQLite image | 2,500 | 4.81 ms | 2.20 ms | 4.92 ms |
| SQLite image | 5,000 | 8.92 ms | 2.44 ms | 9.75 ms |
| SQLite image | 10,000 | 17.48 ms | 2.78 ms | 20.48 ms |

"First read" runs from import start to a read queued after the first committed
change. It returns with 1,000 rows for rows segments or 1,024 rows for images.
During eviction, the first read returns after 2.07 to 2.22 ms with the first
1,024 rows removed and later cleanup pending. The indexed FTS identity map
removes repeated source-ID scans during deletion; chunk commits and mapping
maintenance add import work (the 10,000-row image import takes 24% longer than
a single transaction would). Image copying stays automatic, with no
responsiveness or throughput switch.

These medians describe a local diagnostic. They do not establish production
latency or native-core throughput. The browser suite separately checks real OPFS
reads after the first committed image chunk, incomplete coverage, a crash after
that chunk, and retry in the same session. Native binding scheduling and large
first-page scope clears have no latency measurement.

## Imports with pending edits

Imported rows and pending edits interact when the imported table has a secondary
unique index and a pending edit exists. The Rust core restores imported and
pending row identities from server state, then replays that table's pending
edits in order; unrelated tables stay intact. The benchmark uses optimized
builds, in-memory SQLite 3.46.0 on Apple M4, one pending insert, secondary
unique indexes and managed FTS on both tables, and 8,192 rows in the unrelated
table, with one warmup and three measured trials per size. The clock covers
image application:

| Imported rows | Median | Full table rebuilds |
|---:|---:|---:|
| 10,240 | 32.04 ms | 0 |
| 51,200 | 164.78 ms | 0 |
| 102,400 | 345.59 ms | 0 |

Regression tests compare rows and image imports with a full-rebuild reference,
including unique values freed or occupied by incoming rows, pending updates and
deletes, typed primary keys, FTS contents, and rollback. A scaling test rejects
any copy of the unrelated table. Reconciliation work grows with the pending
operations for the imported table. Pending deletes with floating-point keys keep
the text-match scan. The runs exclude disk-backed imports and binding queue
latency. A host that serializes reads behind synchronization needs a separate
read connection; yielding inside the Rust core does not provide one.

## Advanced: diagnostic workloads

This section documents the benchmark harness for contributors who measure
replay, fanout, reconnect, reads, blobs, and the native byte envelope. The
commands write versioned JSON artifacts to `bench/results/` and leave the
curated record unchanged. [`bench/README.md`](https://github.com/syncular/syncular/blob/main/bench/README.md) defines options, phase boundaries,
and comparison rules.

```sh
bun run bench --workload replay --lane socket --storage file --sizes 1000
bun run bench --workload reconnect --lane socket --storage file --sizes 1,5,25
bun run bench --workload replay --core rust --lane socket --storage file --sizes 1000
bun run bench --workload replay --core rust --lane engine --storage file --sizes 1000
```

### Lanes, processes, and durability

The socket lane uses full TypeScript or Rust clients, the shipping HTTP and
WebSocket transports, and a separate repository-owned server process. The
TypeScript engine lane runs the same fixture through the in-process seam. Both
lanes accept `--backend postgres` with `SYNCULAR_PG_URL`; each Postgres attempt
owns an isolated schema and removes it during cleanup. The SQLite benchmark
server uses an in-memory database, and file storage applies to the client
replicas. Use the Postgres backend to measure a persistent server; the client
SQLite durability check does not describe server persistence.

Socket replay, fanout, and reconnect give every TypeScript or Rust writer and
reader its own process, with a separate server process. TypeScript engine clients
share a process; Rust engine replay runs each client on a Bun worker in the
server and controller process. Artifacts record the execution model, per-client
OS resources, and the actual SQLite version, journal mode, and synchronous
setting. File clients require WAL and FULL; memory clients require the memory
journal and FULL. A different effective configuration fails the attempt. The
metadata queries run outside operation timers, including the reopen timer.

Persistent Bun and Node clients use WAL journaling with `synchronous=FULL`, and
the default factory keeps each commit durable. SQLite creates adjacent `-wal`
and `-shm` files, so close all connections before you copy the main database
file, or use SQLite's backup facilities. This setting does not change browser
OPFS storage. `serverMetrics.database` records the SQLite version and
durability, or the Postgres version and allowlisted durability settings read
through the benchmark pool. It excludes database URLs and credentials.

Process-backed workloads record CPU milliseconds and peak RSS bytes for each
client after exit. These counters include setup, validation, stdio, and
shutdown, and exclude the server and controller. Peak RSS is each process's
lifetime high-water mark, so adding reader peaks does not give simultaneous
memory usage. Artifacts retain source hashes, raw attempts, final-state digests,
method counts, and resource boundaries.

### Replay

Replay measures an offline writer's queue draining to the server and independent
readers observing it. Socket replay retains original commit identities,
acknowledgements from every round, operation construction and drain times, and
per-client lifetime CPU and peak memory.

The runners validate writer and reader rows against the seeded fixture and the
declared edits; matching clients alone cannot satisfy the check. They also
verify the original commit IDs in the durable outcome journal, empty outboxes,
and the exact server sequence. These checks run outside observation latency.

The TypeScript socket replay contract checks actual SQLite commit calls for 501
queued commits and allows at most 520. Consecutive successful acknowledgements
share one local transaction, and each commit keeps its own durable outcome. See
[successful acknowledgement batches](/reference-outbox-outcomes/#acknowledgement-batches) for the change-event boundary.

TypeScript process replay attributes SQL shapes and counts rows returned by
successful queries; bound values and returned row contents stay out of the
measurements. `clientSqlite.run` records transaction-control calls separately
from `database.transaction`, so nested savepoints stay distinguishable from
`COMMIT`. Their durations overlap the outer database and drain timers. Full
outbox-read row counts measure the pending bodies materialized for replay, and
counts exclude construction after the replay reset. Async method and SQL-shape
measurements include `pending`, `maxPending`, and `overlappingCalls`, which
measure overlap at the instrumented method boundary and do not separate executor
queueing from database execution. A reset starts a new collection epoch.

Rust engine replay runs behind a private benchmark transport that calls the real
async server and realtime session through a shared response buffer. It retains
independent readers, individual commit IDs, FIFO order, and file-backed SQLite
durability checks. Direct and shared-command operation timers include host
callback scheduling, SSP2 copies, and server work, and exclude outer command
JSON and worker delivery. Artifacts record the private library hash and thread
identities; CPU and RSS cover the shared process. Shipping FFI measurements use
their own boundary. Other Rust engine workloads are unsupported.

Rust socket workloads build the native driver in release mode and run each
client in its own process. `--boundary command` times the shared command router;
the default times direct core operations. Parent elapsed time includes stdio
delivery.

### Restart

The restart workload runs on TypeScript and Rust with socket transport and file
storage. It terminates the offline writer, opens its database in a fresh process,
verifies the persisted queue, and checks convergence after replay. The artifact
keeps the killed and the reopened writer separately.

### Fanout and reconnect

Fanout and reconnect run one writer process and many reader processes against a
separate server process. Reconnect artifacts retain the explicit sync duration
in `observations[].reconnectSync.elapsedNs`, followed by a separate
acknowledgement wait; both intervals sit inside controller elapsed time.

Both client cores commit each incoming `COMMIT` frame and rows-segment block in
its own local transaction, and each observer-visible transaction publishes its
own revision. A later failed frame preserves the committed prefix, and the
cursor advances only after a successful `SUB_END`.

Native realtime I/O uses socket readiness and explicit send notifications, and
acknowledgements keep their per-delta boundaries. A Rust replica with no pending
writes applies changed rows directly to its visible tables inside the existing
observation transaction. Appending a local Rust commit applies its operations to
the current optimistic overlay. An incoming frame that touches tables without
secondary unique constraints reconciles the changed rows and replays only their
pending operations in FIFO order; other pending rows keep their visible values.
Frames that touch a table with secondary unique constraints, and queue removals,
rebuild the overlay from confirmed rows and the surviving queue. Each frame keeps
its own durable revision and rollback boundary, and a failed durable append or
revision write leaves no queued commit and no visible mutation.

### Commit boundaries

`--workload commit-boundaries --lane socket` measures three commits with 499/2/1
or 500/2/1 operations. `--reject-middle` rejects the middle commit through the
server validator. The runner verifies rollback of both middle writes, successful
application of the later independent commit, exact request and acknowledgement
identities, and the durable rejection outcome. TypeScript and Rust use the same
fixture against SQLite or Postgres.

### Reads

`bun run bench --workload read --lane engine --storage file --iterations 100`
measures warm local reads at 1,000, 10,000, and 100,000 rows. The TypeScript
workload compares the database adapter, public `query`, and `querySnapshot` with
the same SQL and synced data. Primary-key reads return one row and bounded reads
return 100 rows. Snapshots have empty coverage requirements. Artifacts retain raw
samples, rotating execution order, parameters, schema, query plans, and separate
statement counts. The database measurement includes row materialization.
Validation runs outside the latency samples, and each surface must return the
generated fixture in query order. Application indexes and queries stay fixed.

`--core rust --lane socket --boundary direct` measures Rust public reads, and
`--boundary command` includes the shared command router. The fixture bootstraps
over sockets before measurement. Rust measures all iterations inside one process
and keeps a raw baseline on the same SQLite connection. An untimed trace pass
limits raw and query reads to one statement and snapshots to four, including
savepoint and release. `--boundary ffi` measures the exported C call with input
parsing, command dispatch, diagnostics, and response serialization; separate host
samples cover request serialization, response copying, freeing, and JSON
parsing. FFI reads add five diagnostic SQL statements in this fixture, for
totals of six on queries and nine on snapshots.

On macOS, measure the Swift SDK over the native FFI with the same fixture:

```sh
bun run bench --workload read --core rust --boundary ffi --binding swift --lane socket --storage file --iterations 100 --trials 5
```

The runner compiles the Swift SDK as a separate optimized module and builds the
native library in release mode with locked dependencies. Each attempt checks the
loaded library paths and hashes, exact row values, the unchanged revision, the
empty outbox, and SQLite durability. Samples cover the complete Swift `query`
and `querySnapshot` calls, including Foundation serialization, command dispatch,
FFI execution, and result decoding. Three warmup cycles precede alternating
surface order. The event poll loop stays active on its background queue with a
dedicated serial delivery queue and no application callback. UI rendering and raw
SQLite timing are outside the profile. Swift samples and the Rust caller's FFI
call samples have different measurement boundaries. Kotlin, Flutter, React
Native, and Tauri runtime costs have no read measurement.

The FFI and Tauri diagnostic observers compare typed snapshots before they build
an event's JSON, so unchanged evidence avoids JSON fingerprint allocation. The
observers still refresh storage and client state and ignore only capture time
when comparing snapshots; changed events keep the current capture time. Rust
scope lookups, row deletes, and CRDT row reads reuse prepared statements. For
string, JSON, integer, and boolean keys, their predicates seek the existing
primary-key index and keep the exact text comparison. Floating-point keys keep
the text predicate because SQLite can render distinct values as the same text.
Rust diagnostic storage aggregates reuse the connection's prepared statement
cache for outbox, outcome, and blob byte estimates and read current values on
every call; page-count and page-size pragmas stay uncached.

### Blob lifecycle

`--workload blobs --lane socket --storage file` runs TypeScript staging, upload
and reference commit, fresh download, cache hit, and interrupted-download
recovery. The full profile uses 64 KiB, 2 MiB, and 16 MiB bodies, including two
distinct 2 MiB objects. Validation checks exact bytes, upload pins, live
reference counts, clean recovery, and cache hits without network requests. The
engine lane runs the same fixture through the in-process Hono route. Each phase
reports database and transport call counts, failures, and inclusive durations,
with SQL statement shapes that omit bound values. SQL time overlaps method and
transaction time, so do not sum these durations.

`--core rust --boundary direct` or `--boundary command` runs the native HTTP
client. Artifacts separate native operation time from stdio delivery, response
framing, parent JSON parsing, and hex decoding, and record serialized byte
counts. Framing records received chunks and newline search ranges, so controller
work separates from native operation time. The native interruption uses a
one-use signed URL whose HTTP body ends early; the client must leave the cache
empty and request authorization again to recover. Rust file-profile blob runs
time the owned `FetchedBlob` result, and `--blob-reference-rows 100000` seeds
that many visible references outside the operation clock and verifies that cache
trimming keeps the downloaded body.

`--boundary ffi` runs the shipping C ABI through a Rust caller. Its phases
separate the complete C call from request serialization, returned-string
copying, release, and host parsing, and server request traces verify cache hits
and recovery through the FFI-owned native transport. Language-binding runtimes
have no blob measurement.

The shipping blob command moves its owned result into the reply envelope, and
the C ABI moves that reply into its outer envelope. The C ABI borrows parsed
command parameters for the duration of dispatch. These paths keep the JSON
format and avoid full-payload clones; a structural Rust test counts
payload-sized allocations separately from timing and process memory profiles.
Query and snapshot commands borrow their bind arrays and move row maps into the
result, and snapshot metadata keeps its shared serializer.

### Permission purge

`--workload purge --lane socket --storage file` runs on TypeScript or Rust
clients. `--sizes 2000,10000,100000` selects the rows in the revoked project;
one additional row belongs to a retained grant. Rust supports direct and command
boundaries. The private server fixture removes the project grant through its
scope resolver, and grant removal completes before timing. The measured explicit
sync round includes authorization and local purge; discovery of a grant change
is outside the workload.

Each attempt verifies the revoked subscription and reason code, exact retained
row values, an unchanged authoritative commit sequence, and an empty outbox. It
closes the client, reopens the same SQLite file with the same identity in a
fresh process, and verifies that the purged rows stay absent before and after
another sync. Artifacts separate client operation time, controller elapsed
time, reopen time, SQL and transport attribution, and per-process lifetime
resources. Validation reads stay bounded across data sizes.

```sh
bun run bench --workload purge --lane socket --storage file --trials 5
bun run bench --workload purge --core rust --lane socket --storage file --trials 5
bun run bench --workload purge --core rust --boundary command --lane socket --storage file --trials 5
```

### Native byte envelope

`--workload native-bytes` measures the shared Rust encoder and JSON conversion
phases in a release build of the native benchmark driver. Phase timings exclude
platform binding delivery and network download. The Rust byte decoder converts
ASCII pairs directly while it preserves its accepted inputs and errors. Ten
paired local trials measured 16 MiB envelope decoding at 14.7 ms and
shared-command staging at 120.8 ms. These measurements cover native command processing on the
benchmark host; complete binding delivery needs separate measurements.

### Native phases and SQL counts

Rust socket replay, restart, commit-boundaries, fanout, and reconnect accept
`--native-sql` to record SQL verb counts and commit and rollback hook counts from
reset through acknowledgement. Commit hooks include outermost savepoint release
and implicit writes, and run before the commit. The collector keeps only fixed
verb labels and counts, and SQLite's internal SQL expansion adds instrumentation
overhead, so run ordinary timing comparisons without the flag. Direct and
command boundaries support it; engine and FFI boundaries reject it.

Rust socket replay, restart, commit-boundaries, fanout, reconnect, and blobs
also accept `--native-phases` on Linux and macOS with direct or command
boundaries. It records per-client wall time and calling-thread CPU for
request and row encoding, decode, apply, upsert execution, pending replay,
observation and cursor persistence, and blob download and cache work. Blob
snapshots separate each download, cache hit, failed download, and recovery.
Fixed names and counters exclude row values and identifiers. Failed calls count,
and a reset starts a fresh interval.

The phases are inclusive and overlap, so do not add their durations. Thread CPU
excludes transport I/O threads, the server, and the controller. Timing adds
overhead and requires a comparison with phases disabled. The recorder exists
only in the private benchmark feature; public diagnostics, command and FFI
envelopes, and SSP2 are unchanged. Replay and observation store snapshots under
client `stats.phases`; blob samples use `nativePhases`.

### TypeScript sampling profiles

`--ts-profile` works with TypeScript socket replay, restart, commit-boundaries,
fanout, and reconnect, and retains a Bun sampling profile for each isolated
client. The writer and reader stats hold compressed raw stacks alongside SQL and
transport measurements. Collection begins after setup and ends before final
validation, and profile formatting and compression run outside delivery timers.
Sample counts identify observed call stacks and can include native waits; they
do not measure exact CPU time.

### PostgreSQL

Postgres replay artifacts include SQL shapes with bound values omitted and the
awaited local realtime notification duration for HTTP and socket pushes. SQL
durations overlap their transaction methods, and reader cursor persistence
overlaps writer transactions, so these totals do not add up to replay elapsed
time. Notification completion excludes the subsequent client apply and cursor
persistence.

CI runs a separate Postgres diagnostic job for TypeScript and Rust socket
clients. Each job owns its database service and keeps five fresh 1,000-commit
replay attempts and five 25-reader reconnect attempts with file storage. Invalid
state or an unavailable Postgres fails the job, and timing thresholds await
runner calibration. The reduced replay and reconnect CI workloads enforce FIFO
boundaries and convergence without host-speed thresholds.

`--pg-io` records WAL I/O for an explicit Postgres run:

```sh
SYNCULAR_PG_URL=postgres://postgres@127.0.0.1:5432/syncular_bench bun run bench --workload replay --lane socket --backend postgres --storage file --sizes 1000 --trials 5 --pg-io
```

Use an isolated PostgreSQL 18 instance with `track_wal_io_timing=on`. The runner
records server durability settings and cumulative WAL and checkpoint statistics
before setup and after all benchmark database sessions close, and it leaves
settings and counters unchanged. A reset or failed observation marks the attempt
failed. The ordinary Postgres benchmark needs no I/O observer or extension. The
counters include setup, bootstrap, validation, and cleanup, and stay
cluster-wide; background PostgreSQL processes have separate backend-type rows.
Their durations overlap existing server measurements and cannot be summed into
replay latency. Use them to investigate durability costs alongside writer drain
and independent reader visibility.
