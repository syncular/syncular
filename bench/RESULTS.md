remains automatic; there is no application responsiveness/throughput switch.

## Rust imports with unique indexes and pending edits (2026-09-13)

The review found that each image chunk rebuilt every visible table and its FTS
projection when the imported table had a secondary unique index and a pending
edit. The fix restores imported and pending row identities from server state,
then replays that table's pending edits in order. Unrelated tables remain intact.

The same ignored native benchmark ran against `677aed3e` and the candidate source
identified below. Both used optimized builds, in-memory SQLite 3.46.0 on Apple M4,
one pending insert, secondary unique indexes and managed FTS on both tables, and

trials, baseline first. The clock covers image application; fixture creation and

Separate regression tests compare rows and image imports with a full-rebuild
reference, including unique values freed or occupied by incoming rows, pending
updates/deletes, typed primary keys, FTS contents, and rollback. The scaling test
rejects any attempt to copy the unrelated table.

These timings measure native core throughput with one pending edit. Reconciliation
work still grows with the pending operations for the imported table. Pending deletes
with floating-point keys retain the existing text-match scan semantics. These runs do not
measure disk-backed imports, binding queue latency, or Diego's original dataset.
A host that serializes reads behind synchronization still needs a separate read
connection; yielding inside the Rust core does not provide one.

The candidate stores upload state outside the immutable body row, writes
commit dependencies directly with the outbox commit, and reads live references
only during cache retention. It removes stored refcounts, four triggers,
startup backfill, reconciliation, and cache-hit writes. A fresh download
checkpoints its completed body from WAL before returning. Every candidate
download had a zero-byte WAL before the cache-hit measurement.

TS fresh-download claim. Reopened cache hits improved in both cores and both
collections. Compact observations and the analyzer are under

## SQLite blob download reconciliation in 0.18.0 (2026-09-11)

The file profile downloaded one 65,536-byte object into a persistent client
with 100,000 visible `blob_ref` values. Each core ran ten paired baseline and
candidate blocks through MinIO, then repeated the complete collection with new
containers. The operation clock includes transport, SHA-256 validation, SQLite
cache insertion, reference reconciliation, cache-cap enforcement, and complete
byte materialization. Fixture creation and final digest validation stay outside
the clock.

| Collection | Core | Baseline median | Candidate median | Paired change (95% interval) | Median saving |
| --- | --- | ---: | ---: | ---: | ---: |
| First | TS | 48.68 ms | 18.78 ms | -61.72% [-63.70%, -59.10%] | 30.56 ms |
| First | Rust | 38.42 ms | 15.75 ms | -59.55% [-61.56%, -57.56%] | 22.49 ms |
| Confirmation | TS | 49.31 ms | 18.97 ms | -61.57% [-63.13%, -59.83%] | 29.82 ms |
| Confirmation | Rust | 39.01 ms | 14.84 ms | -60.05% [-61.70%, -57.99%] | 23.67 ms |

The candidate asks SQLite to count references for the downloaded body and
updates only that cache row. The baseline selected and parsed every visible
reference, reset every cached refcount, and rewrote the complete count map.
Both confirmation intervals exclude zero, and both median savings exceed the
predeclared 64 KiB A/A floors: 3.267 ms for TS and 10.705 ms for Rust.
Staging, upload plus commit, cache-hit, and reopened-hit confirmation intervals
include zero.

**Lane**: bun:sqlite loopback — the TS client core and the real
server library exchange in-process SSP2 bytes (transport, segment download
and realtime are direct function calls / RealtimeHub callbacks). Same
philosophy as the conformance loopback: no sockets, no HTTP stack, no
browser — and the client runs on bun:sqlite, not sqlite-wasm. Read every
number as the in-process best case: a real deployment adds network and
serialization costs this lane does not have.
